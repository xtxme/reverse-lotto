# Investigation 1 — Why Do Most Submissions Appear After Betting Closes?

Phase B, 2026-11-07 (Asia/Bangkok). This file validates the Phase A claim against newly captured raw row timestamps and extends it to seven consecutive rounds.

## 1. Mandatory audit result

Phase A reported for round 55 (period 231):

- 151 submissions total,
- 5 before the 19:30:00 betting close,
- 146 at or after the close,
- 51 at 19:31:59 and 49 at 19:31:43.

The original Phase A artifacts did **not** contain the per-row timestamps needed to verify these claims: `round_229_numbers.csv` and `round_230_numbers.csv` stored only `seq,number`. The 151-row round 55 list was reconstructed in-browser but not saved row-by-row. That was a genuine evidence gap.

Phase B closed the gap by re-fetching the complete, public, sanitized row lists for periods 229–235 (rounds 53–59) and storing them as:

- `phase_b/evidence/raw_rounds/round_229.json` … `round_235.json`
- `phase_b/evidence/submission_events.csv` (round, period, seq, number, timestamp, offset, bucket)
- `phase_b/submission_timeline.csv` (per-round summary)
- `phase_b/submission_timeline_events.csv` (1,097 per-row events; copy of `evidence/submission_events.csv`)

No usernames are stored. Only `seq`, 5-digit number, and timestamp are retained.

## 2. Definitions used

| Term | Meaning in this report | Source |
|---|---|---|
| Betting close | `close_date` of the round; betting must stop | Server `betconfig` (observed for round 55 as `2026-11-07T12:30:00Z` = 19:30 local); schedule grid for other rounds |
| Shoot close | `close_date + 2 minutes`; the number-submission window ends | `closeDateYeekee` in server payload; `expireTimeOfShootNumber = 120000` in client code; observed last timestamps at `close+1:59` |
| `created_at` | The timestamp displayed for each submission | Server-rendered HTML and JSON list endpoint |
| Before close | `created_at < close_date` | Recomputed per row |
| After close | `created_at >= close_date` | Recomputed per row |

The close times for rounds 53–59 are on the observed 15-minute grid: 19:00, 19:15, 19:30, 19:45, 20:00, 20:15, 20:30. Round 55’s close was independently confirmed from its server `betconfig`. The grid anchor (round 52 = 18:45) was directly observed in Phase A.

## 3. What `created_at` is — and is not

OBSERVED:

- The timestamp is a Bangkok-local string with **one-second precision** (`YYYY-MM-DD HH:mm:ss`), no milliseconds.
- It is delivered by the server in the HTML and in the JSON list endpoint; it is not generated by the browser.
- The site’s own rules state that displayed submission time uses real server time.
- Server `Date` headers and the local clock agreed within ±1 second during Phase A.
- The API and the server-rendered page show the same timestamps and the same order.

INFERRED:

- `created_at` is most likely the database insert/commit time for the submission row.
- It could alternatively be the time the queue worker accepted or processed the row. The available evidence cannot distinguish creation, acceptance, and processing.
- It is **not** a client-side local-time conversion and it is **not** the time the browser first displayed the record.

UNKNOWN:

- Whether the value is set by the application at request handling, by a queue worker, or by a database default.
- Whether a batch process assigns identical timestamps to many queued rows.

## 6. Does the visible sum reflect every accepted submission?

OBSERVED:

- For round 55, at 19:32:01 the list endpoint returned `sum = 7,422,657`; the final page displayed the same sum, and the sum of all 151 rows equals 7,422,657.
- During the earlier window, the sum grew as rows appeared: 0 → 46,128 → 47,592 → 177,809 → 188,748 → 7,422,657.
- For rounds 53 and 54, the CSV sum matches the displayed sum exactly (9,281,577 and 7,724,164).
- The final result for rounds 53–59 is exactly reproducible from the full row set using the published rule.

INFERRED:

- The `sum` field is the sum of all rows the endpoint currently considers accepted in that period. It is not merely the sum of the 20 returned rows: 20 rows clearly cannot sum to 7.4 million at ~46k each.

UNKNOWN:

- Whether a row can be accepted by the server but omitted from the list/sum temporarily (e.g., inside a transaction or queue). No such row was observed.

## 7. Could delayed rendering or delayed retrieval explain the pattern?

No.

- The timestamps are server-side values stored with the rows; they are not the time the browser rendered them.
- The browser fetched the page after the fact; the timestamps inside the HTML already showed the pre/post-close split.
- A delayed network response would shift the **observation** time, not the `created_at` values.
- The sum and row count at 19:32:01 were already final; the page was not still receiving rows.
- The pattern is present in every one of seven independently fetched rounds.

Classification: OBSERVED that rendering delay is not the explanation; INFERRED that the timestamps reflect server-side event times.

## 8. Is the pattern consistent across rounds and time of day?

Yes, for the seven consecutive rounds observed (53–59, spanning 19:00–20:30). The pre-close share was 0%–3.31%, and the final-20-second share was 77.5%–88.7%. The two dominant bursts occurred at the same offsets in every round (+103 s and +119 s; see Investigation 2).

Not tested: other days, early-morning rounds, or rounds with abnormal volumes. The seven-round sample is enough to reject “isolated observation” but not enough to characterize seasonal or day-of-week variation.

## 9. Normal user activity vs batch processing

The evidence distinguishes some hypotheses:

| Hypothesis | Evidence for | Evidence against |
|---|---|---|
| Many users independently submit near the deadline | 51/49/53/65 rows in a burst; each row has a distinct masked user; numbers are mostly unique | The bursts occur at exactly +103 s and +119 s in 7/7 rounds, which is too regular for independent human timing |
| One automated client submits many rows | High burst counts | Each row in the top burst has a distinct masked user; max rows per user in a burst = 1 (except round 59, where one user had 2) |
| Server batch/queue assigns timestamps to many users’ rows | Identical timestamps across many distinct users; two fixed offsets; no submissions after +119 s | No server logs; cannot observe queue or transaction boundaries |
| Delayed browser rendering | — | Timestamps are server-side and already final at retrieval; rendering delay cannot change `created_at` |

The most defensible conclusion:

- **OBSERVED:** the bursts are multi-user and multi-number, not one user’s batch.
- **HYPOTHESIS:** the two fixed offsets are produced either by a server-side batch/queue flush or by many clients synchronized to the same deadline pattern.
- **UNKNOWN:** which of those two is true. Operator-side request logs, queue metrics, or IP/device data would be required.

## 10. What cannot be established without operator logs

- The difference between request arrival time and database commit time.
- Whether rows are queued, batched, or inserted synchronously.
- Whether the same physical device/account submitted multiple rows in a burst.
- Whether rate limits or anti-automation controls exist server-side.
- Whether the two fixed offsets are scheduled jobs or emergent user behavior.
- Whether any rows were rejected or retried.
