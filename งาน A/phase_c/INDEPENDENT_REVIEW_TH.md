# Phase C — สรุปและข้อสังเกตจากการตรวจอิสระ

วันที่ตรวจ: 8 พฤศจิกายน 2026 เวลาไทย
ขอบเขต: อ่านเอกสาร Phase C ทั้งหมดและสคริปต์ 3 ไฟล์ ตรวจข้อมูล CSV/JSON ทุกแถวและภาพ 2 ภาพ คำนวณตัวเลขหลักซ้ำจากข้อมูลที่ส่งมา ไม่ได้เข้าเว็บไซต์สดหรือดึง REA ledger ต้นฉบับใหม่ รายงาน OpenCode ต้นฉบับเก็บไว้ตามเดิม

## ข้อมูลและผลที่ตรวจซ้ำได้

- 16 รอบ: รอบ 53–68 / period 229–244 รวม 2,474 แถว เป็นข้อมูลวันหวยเดียวกันของ 7 พฤศจิกายน 2026 ไม่ใช่ข้อมูลข้ามวัน รายการสุดท้ายของชุด pool สิ้นสุด 22:46:59 ส่วนการสังเกตหน้า grid ต่อถึงหลังเที่ยงคืนเป็นคนละส่วน
- 7 รอบแรกซ้ำกับขอบเขต Phase B จึงไม่ใช่ตัวอย่างใหม่อิสระทั้งหมด
- user_hash คือ SHA-256 ของข้อความชื่อแสดงผลที่เว็บไซต์ปิดบังแล้ว เติม prefix คงที่ phase_c: และตัดเหลือ 16 hex เป็นนามแฝงของ display identifier ไม่ใช่ ID บัญชีจริงหรือบุคคลจริง
- พบ 469 hashes; 286 ปรากฏอย่างน้อยสองรอบ (61.0%); 19 คู่ hash+เลขปรากฏอย่างน้อยสองรอบ
- กลุ่มเลขซ้ำ 104 กลุ่ม / แถวส่วนเกิน 120 / คู่เลขซ้ำ 138; 94 กลุ่มเป็น hash เดียวทั้งหมด, 4 mixed, 6 ต่างกันทั้งหมด; ไม่มีกลุ่มที่ทุกสำเนามีเวลาเดียวกัน; คู่เวลาเดียวกัน 3/138
- สอง burst ที่ T+103 และ T+119 วินาทีมี 777 และ 749 แถว รวม 1,526/2,474 = 61.68%; แถวแสดงผลที่ 16 มี offset +119 ทุก 16 รอบ
- มีเวลาเพิ่มขึ้นระหว่างแถวติดกัน 18 จุด จากคู่ติดกัน 2,458 คู่ (0.73%); ทุกจุดเพิ่ม 1 วินาที จึงไม่ใช่ timestamp descending อย่างเคร่งครัด
- จำนวนแถว Timestamp ก่อนเวลาปิดใน 16 รอบ: 2,1,5,1,2,1,0,5,5,9,1,0,1,0,0,0 รวม 33 (1.33%); ตั้งแต่ปิด 2,441 (98.67%); ทุกครั้งยังน้อยกว่า 16

## ประวัติย้อนหลังและ REA

รายงานระบุ grid เพิ่มจาก 51→53→59→62→71→72 ผลตามเวลาที่เก็บ จึงอธิบายว่าไฟล์ 53 ผลเป็น snapshot ไม่ใช่คลังผลคงที่ หน้า result ที่ทดลองเปลี่ยนวันที่ให้ประวัติสินค้า 264 รอบ แต่ไม่ให้ประวัติรายวันของสินค้า 88 รอบ ห้ามใช้สองสินค้าปะปนกัน

ควรสรุปว่า "ไม่พบประวัติสินค้า 88 รอบผ่าน UI/เส้นทาง/วันที่ที่ทดสอบ" ไม่ใช่พิสูจน์ว่าไม่มี archive หรือข้อมูลในฐานข้อมูลที่ใดเลย สาเหตุ period เก่า 404 และระยะ retention ยังไม่ทราบ ไม่มี completed-day snapshot ครบ 88 ผล

REA ตามรายงานเห็น list-number 1 request ใน 65 วินาทีบน detail และ 0 allowed-origin requests ใน 70 วินาทีบน list; main.js hash ตรงของเดิม ช่วยสนับสนุน sparse polling แต่ไม่วัด exact 60s (ตัวเลขนั้นจาก Phase B agent-browser) ไม่ยืนยัน historical filters, row-level timestamps หรือสูตรทั้งหมด ตัว evidence ID ในเอกสารเป็นตัวอ้างอิง ไม่ใช่ผลตอบกลับดิบที่แนบครบให้ตรวจอิสระ

## สถิติที่ตรวจซ้ำเพิ่มเติม

- H2 product ∏(b119/n) = 4.3214564e-9 คำนวณได้ แต่สมมติฐาน random position ไม่เหมาะกับตารางที่จัดล่าสุดก่อน กลุ่มเวลาสุดท้ายมี 34–65 แถว จึงคาดได้ว่าแถว 16 อยู่ในกลุ่มนี้ ไม่ใช่หลักฐานการเลือกพิเศษหรือการจัดฉาก
- H3 สุ่มสลับ hash ภายในรอบ 10,000 ครั้ง (ตรวจเพิ่ม seed 20261108): ค่าเฉลี่ย null 0.5603, SD 0.7507, max 6 เทียบพบจริง 94; ไม่พบ simulation ถึง 94; plus-one empirical p = 1/10001 ≈ 0.00009999 ผลคือความสัมพันธ์ระหว่างเลขกับ display identifier แตกต่างจาก null ไม่ได้พิสูจน์เจตนา บอต หรือผู้ควบคุม
- H4 hypergeometric ต่ำสุดรอบ 59 p = 0.01099258; หลัง Holm/BH 16 tests ค่าต่ำสุด ≈0.17588126 ไม่ผ่าน 0.05 ภายใต้ null ที่ใช้ ทั้งนี้ null ไม่แทนพฤติกรรมทุกบัญชีจริง และการไม่ปฏิเสธไม่ได้พิสูจน์ว่าไม่มี coordination

## ข้อที่ต้องแก้หรือจำกัดถ้อยคำ

1. ข้อความก่อน cutoff มี 0–5 แถวใช้ได้เฉพาะ 7 รอบเดิม ชุด 16 รอบสูงสุด 9 แถวในรอบ 62 รวมก่อนปิด 33 แถว ยังเป็นการกรอง Timestamp ย้อนหลัง ไม่ยืนยัน first-seen visibility ก่อนปิดจริง
2. สมมติฐานเปิดรับเลขเฉพาะ T−2 นาทีไม่สอดคล้องกับข้อมูลใหม่: รอบ 61 มีรายการก่อนปิด 778 วินาที รอบ 60 ก่อน 392 วินาที ไม่ควรใช้ชื่อ bucket before_shoot_open เป็นหลักฐานว่ารายการนั้นอยู่นอกช่วงที่เซิร์ฟเวอร์อนุญาต
3. ชื่อปิดบังเหมือนกันอาจเป็นคนละบัญชี; หลาย hash อาจอยู่ภายใต้ผู้ควบคุมคนเดียว จึงตัดสมมติฐานบอตเดียวหลายบัญชีไม่ได้
4. คู่ inversion มี hash/เลขต่างกันไม่ได้หักล้าง sorting ตาม hash/username ต้องตรวจ comparator จริง และ hash ไม่รักษาลำดับอักษรของชื่อเดิม
5. ไม่พบ sorting เลขขึ้น/ลงภายในกลุ่มเวลาเดียวกันโดยรวม แต่ยังไม่รู้ internal key; ห้ามจัดเรียงใหม่แล้วแทน display row16
6. กลุ่ม +119 ยืนยันรูปแบบ Timestamp ไม่ได้พิสูจน์ว่าข้อมูลเพิ่งมีหรือเพิ่งมองเห็น ณ วินาทีนั้น เพราะ created_at semantics และ first-seen ยังไม่ทราบ
7. ผล H1/H2 ใช้บางข้อมูลที่รู้มาก่อนจาก Phase B ควรแยกเก่ารอบ53–59 กับเพิ่มรอบ60–68 ไม่เรียกทั้ง16เป็น holdout อิสระ ไม่มีหลักฐาน timestamped preregistration ให้ตรวจว่าล็อกสมมติฐานก่อนอ่านข้อมูลใหม่
8. พฤติกรรม 16 แถวรอบ62เป็น outlier ไม่พิสูจน์ automation; ระยะห่างไม่เท่ากันทุกครั้ง มี 16–18 วินาทีหลายช่วงแต่มีช่วงยาวกว่า และ Timestamp อาจเป็น processing time
9. รอบ88ปิดเดิมพัน03:45 แต่ถ้าปิดส่งเลข+2นาทีต้องอย่างน้อย03:47ก่อน processing; ไม่ควรบอกครบ88ผลทันที03:45 เวลา grid/reset จริงยังไม่สังเกต
10. ข้อผิดพลาด Phase B เดิมยังไม่ได้แก้ในไฟล์ต้นฉบับ: พาลินโดรมคาดหมาย10.97ไม่ใช่1.10; autocorrelation ต้อง bottom+top ไม่ใช่ top+bottom (r≈−0.1705, permutation p≈0.2109 จากการตรวจเดิม); pool53+54ซ้อนชุดผล1–53เฉพาะ53; LOOเดิมมีข้อมูลรอบอนาคตจึงไม่ใช่ chronological prospective test

## ข้อสรุปเพื่อวิเคราะห์ต่อ

สคริปต์ 3 ไฟล์ที่แนบมาสร้างชุดข้อมูลและสถิติเชิงพรรณนาได้ แต่ไม่เก็บโค้ด permutation, hypergeometric หรือ product H2 ตามรายงาน การตรวจสถิติข้างต้นจึงเป็นการคำนวณเพิ่มจากข้อมูลดิบ ไม่ใช่การรันโค้ดทดสอบต้นฉบับที่แนบมา; ควรเพิ่ม seed, null, correction และ output เพื่อทำซ้ำได้ทั้งหมด ค่า plus-one p จาก permutation มีความไม่แน่นอน Monte Carlo และไม่ใช่การรู้ tail probability ที่แท้จริงอย่างแม่นยำ

หมายเหตุการเผยแพร่: ข้อความใน README ต้นฉบับที่บอกว่ายัง commit/push ไม่ได้เป็นสถานะเก่าขณะสร้างงาน OpenCode; ไฟล์ Phase C และบันทึกตรวจนี้จัดเตรียมเพิ่มเข้า repository โดยแยกจากรายงานเดิม

Phase C เพิ่มหลักฐานเชิงพรรณนาและการทำซ้ำระดับ display identifier ได้มากขึ้น และยืนยัน ordering inversions ที่เคยพบ แต่ยังไม่ระบุสาเหตุ burst, internal sorting key, created_at semantics, ตัวตนหรือผู้ควบคุมบัญชี, retention และพฤติกรรมข้ามวัน ไม่มีการทดสอบความสามารถทำนายผลอนาคตใหม่

งานต่อควรแก้ข้อผิดพลาดเชิงวิธีวิจัยก่อน เก็บ first-seen snapshots พร้อมเวลาและแหล่งหลักฐาน ตรวจหลายวันและหลายช่วงเวลา แยกการจำลองเชิงพฤติกรรมจากสูตรเลขคณิต และทดสอบสมมติฐานที่ล็อกไว้กับข้อมูลอนาคต การตรวจกลไกคิว/commit/order จริงต้องอาศัยข้อมูลจากผู้ดูแลที่ได้รับอนุญาต
