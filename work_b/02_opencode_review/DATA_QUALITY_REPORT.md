## 2. วิธี parse และกติกาการแปลง

### 2.1 รูปแบบไฟล์

```
2026.09.08 วันอังคาร
00:00 FORECASTER_01 📢เว็บ thailotto รอผลออก คะ
00:02 FORECASTER_01 PRIVATE_LINE_GROUP
...
       จับยี่กี รอบที่ 73
            347 - 86
```

### 2.2 กติกาที่ใช้

1. **Date header** `YYYY.MM.DD` เปลี่ยนวันเมื่อพบบรรทัดนี้
2. **Message header** `HH:MM <sender> <body>` โดย `<sender>` ต้องตรงกับรายชื่อที่พบในไฟล์ (10 รายชื่อ) เพื่อไม่ให้บรรทัดในตารางผลถูกตีความเป็นข้อความใหม่
3. **Result block** ใช้ `จับยี่กี รอบที่ N` แล้วอ่าน `TTT - BB` ใน 3 บรรทัดถัดไป
4. **Inline table row** ใช้ `^N: HH:MM ➡️ TTT - BB` เป็นหลักฐานประกอบ (ไม่นับเป็นผลใหม่)
5. **Trading day** นิยามตาม schedule ที่เผยแพร่:
   - รอบ 1 = 06:00 ของวันทำการ
   - รอบ 72 = 23:45 ของวันเดียวกัน
   - รอบ 73 = 00:00 ของวันถัดไป
   - รอบ 88 = 03:45 ของวันถัดไป
   - `trading_day` = วันที่ของรอบ 1 (ไม่ใช่วันปฏิทินของรอบ 73–88)
6. **เวลาปิดรับ** (`scheduled_close`) คำนวณจาก trading day + รอบ; ไม่ใช้เวลาที่ข้อความถูกโพสต์เป็นเวลาผล
7. **Leading zeros** เก็บเป็น string ตลอด (เช่น `038`, `06`, `001`) ไม่แปลงเป็น integer
8. **Deduplicate** ด้วย key `(trading_day, round)`; ค่าที่ขัดแย้งทั้งหมดถูกเก็บใน `outputs/result_conflicts.csv` ไม่ถูก overwrite
9. **Source Line** เก็บเลขบรรทัดของข้อความแรกที่พบผลของรอบนั้น

### 2.3 การตรวจวันข้ามเที่ยงคืน

ตัวอย่างจากไฟล์:

```
2026.08.14 วันศุกร์
00:02 FORECASTER_01 ... จับยี่กี รอบที่ 73 ... 820 - 91
```

รอบ 73 ถูกจัดเป็น `trading_day = 2026-08-13` (ไม่ใช่ 2026-08-14) เพราะเป็นรอบแรกหลังเที่ยงคืนของวันทำการ 2026-08-13 ซึ่งเริ่มรอบ 1 เมื่อ 06:00 ของ 2026-08-13
การจัดแบบนี้ทำให้ลำดับรอบ 1→88 ต่อเนื่องทุกวัน และทำให้วิเคราะห์ lag 1–4 รอบได้โดยไม่ตัดข้ามวันผิด

## 7. Data leakage / look-ahead ที่ต้องระวัง

1. **ห้ามใช้เวลาที่ผลถูกโพสต์เป็นเวลาปิดรับ** — ใช้ `scheduled_close` จาก schedule เท่านั้น
2. **ห้ามใช้ผลของรอบ t+1 ในการคำนวณ trigger ของรอบ t** — ทุก rule ใช้เฉพาะข้อมูลที่อยู่ก่อน target
3. **ห้ามใช้ตาราง inline ที่โพสต์หลังผลเป็น “คำทำนาย”** — ใช้เฉพาะ first-seen ที่โพสต์ก่อนเริ่มชั่วโมง
4. **ห้ามใช้ site archive ที่ดึงหลังเหตุการณ์เพื่อ fill gaps แล้วอ้างว่าเป็นข้อมูล LINE** — แยก dataset `site_complete_results_clean.csv` สำหรับ sensitivity เท่านั้น
5. **รูปทั้งสามไม่มีวันที่/เวลาเผยแพร่** — ไม่สามารถใช้เป็นหลักฐานของ “คำทำนายล่วงหน้า” ได้

## 10. สรุปคุณภาพข้อมูลและความพร้อมใช้

- Dataset หลัก **7,469 รอบ / 87 วัน** มีความสอดคล้องภายในสมบูรณ์: ไม่มีผลขัดแย้ง, headline ตรงกับ inline table 100%
- ค่าที่เทียบกับเว็บไซต์ **7,295 รอบ ตรงกันทั้งหมด**; ช่องว่าง 171 รอบถูกยืนยันว่ามีอยู่จริงบนเว็บ; 14 รอบเป็นรอบอนาคต
- ข้อจำกัดหลักไม่ใช่ “ข้อมูลผิด” แต่เป็น **ข้อมูลไม่ครบ** (187 รอบจาก 87 วัน: เติมได้ 171 รอบจากเว็บที่ยืนยัน, 14 รอบเป็นรอบอนาคต, 2 รอบอยู่ในหน้าที่ถูกตัดออก) และ **ไม่มีข้อมูล prospective** ที่เก็บหลังล็อกสูตร
- เพียงพอสำหรับ:
  - backtest สูตรในภาพ
  - ตรวจคำทำนายรายชั่วโมงแบบ first-seen
  - ทดสอบ pattern/autocorrelation
  - out-of-sample split ตามเวลา
- **ไม่เพียงพอสำหรับ:**
  - ยืนยันว่าสูตรใด “ใช้ได้จริงในอนาคต” (ต้องเก็บข้อมูลใหม่หลังล็อกสูตร)
  - ยืนยันเจตนาหรือความรู้ล่วงหน้าของผู้ให้เลข
  - สรุปเชิงสาเหตุเกี่ยวกับกลไกหลังบ้าน

> **ข้อความสำคัญ:** ผลจากแชตไม่ควรถูกถือเป็น “ข้อเท็จจริงจากเซิร์ฟเวอร์” โดยอัตโนมัติ ถึงแม้จะตรงกับหน้าเว็บ 5 วันเต็มและ 7,295 รอบใน archive ก็ตาม การยืนยันที่ดีที่สุดคือการเก็บข้อมูลใหม่แบบ prospective หลังล็อกสมมติฐาน
